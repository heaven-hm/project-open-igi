# Level 1 scene transcription audit

Date: 2026-10-18  
Scope: model placement, scene rendering, and camera movement used by the Task 1 model viewer.

## Finding

`engine/platform/windows/retail_model_scene.cpp` is a host diagnostic harness. It loads retail level assets, but it is not a transcription of the retail scene loop. It contains host-side model orientation and placement, Direct3D matrix construction, draw batching, and a free camera driven by Windows input. It also owns its window and message loop. These behaviors must not be described as retail natives or treated as the final game scene implementation.

The requested retail rendering, camera, terrain, and world-loop entry points are not yet established well enough to replace this code safely. In particular, the address/name pairs supplied for several camera/render methods conflict with the current analysis evidence. A name in a generated native catalog is a research lead, not proof of the native's role.

## ATTA attachment progress

`MefModel::DynObj_LoadModelMesh` now preserves and decodes each `ATTA` record as a 0x44-byte record. The record stride is established by `Model_GetAttachment` at `0x004D0CF0`; REA/Ghidra evidence `ev_8f35f3877644de667fa64e70a3b5ff5f7cb9676463d7c54999cadd04755d5c65` shows `0x004DFA50` reading the local translation at `+0x10..+0x18` and basis fields at `+0x1C..+0x3C` before composing them with the parent transform.

The child basis now follows the basis-preparation block copied from `scripts/GameNatives/render/004DFA50-Render_MagicObjectTypeSNotD.cpp` and checked with REA evidence `ev_32bb0c07a571b8e1a618bf6ebb1a27bd82b76cfa036d6388e5617c10166a2656`: normalize the first stored column when nonzero, derive the next two columns with the recovered cross-product expressions, then normalize each nonzero derived column. The scene multiplies that result by the parent matrix using the same column layout visible in the factory. A focused fixture checks the recovered cross-product direction, and the Level 1 MEF corpus test loads all 830 assets after this change. This implements only the transform-preparation portion; callback dispatch and child runtime state remain outside the host adapter.

The QVM object reader now retains any symbol-targeted `CALL`, including `DefineMagicObj`, instead of accepting only `Task_New`. Retail startup passes `LOCAL:magicobj` to `Magic_ObjLoad` at `0x004020DD`; its 21-byte body enumerates the supplied path and loads eligible QVM files. The diagnostic scene enumerates the matching `magicobj` directory beside the executable, parses `DefineMagicObj` records, and uses their second string argument as the configured mesh for an ATTA lookup name. The checked retail directory contains two QVMs and 381 such definitions; every one supplies string type and model arguments, matching the first two `Script_GetArg` uses in `scripts/GameNatives/define/004C4520-Define_MagicObj.cpp`. This is the data portion of the `Magic_ObjLoad` / `Define_MagicObj` path; the generic type factory and callback parameters are deliberately not treated as executed.

The diagnostic scene now builds an x86-shaped model/resource/MESH view from each parsed MEF, gets the signed attachment count through `Model_GetAttachmentCount` (`0x004D0D10`), and resolves each record address through `Model_GetAttachment` (`0x004D0CF0`). Both accessors are copied from their address-qualified `scripts/GameNatives` sources. Iteration is capped by the retail MESH count; malformed count/payload relationships are reported and skipped rather than reading beyond the ATTA payload. A read-only pass of the original Level 1 asset directory found 830 MEFs, 88 with nonempty ATTA payloads and positive native counts, and zero MESH-count/payload-stride mismatches. The focused MEF parser and model-loader tests pass. The scene then renders each resolvable named record as a diagnostic child. The value at `+0x40` is retained as an inferred field but does not suppress a child: the available static body evidence does not establish such a filter. Direct MTP instance-name matching remains a host lookup after the configured mesh has been resolved. This wires the verified record accessors into the viewer; the larger `0x004DFA50` MagicObject factory, callback dispatch, and bone state are still not transcribed into the scene.

The missing-model branch is now copied from `scripts/GameNatives/dynobj/004CEC10-DynObj_Missing.cpp`: resolve the requested name, return immediately on success, return null for an empty unresolved name, otherwise resolve `"missing"`. Radare2 disassembly of retail `0x004CEC10` confirms both calls target `0x004CEC40`, the `test eax` success return, the empty-string branch, and the second call with the `"missing"` literal. The scene uses a `HOST HELPER` adapter only because its MTP lookup is not the retail `DynObj_Johan` object registry. Status: `STRUCTURALLY_VERIFIED` for the native branch and `BUILD_VERIFIED` for the adapter; no retail runtime trace has been collected.

### Retail attachment lifecycle cross-check (2026-10-18)

REA/Ghidra analysis of `0x004DEEC0` (`ev_ee13b2a87219e1db615020ee55b0f28e68f999416d4f8a7fafc4292bb5d7489b`) identifies a 1,594-byte function with 46 basic blocks and one pointer argument. Its body calls `0x004DFA50` during first-time object initialization, then walks attached-object state and dispatches type/event callbacks through the global callback table. Independent local Radare2 analysis of the same retail executable reports a 1,594-byte cdecl function, 46 basic blocks, 77 CFG edges, and one stack argument. The catalog candidate `scripts/GameNatives/render/004DEEC0-Render_BindTexture_15.cpp` therefore has a misleading name: this address is part of the MagicObject lifecycle, not a simple texture-binding routine. Its function extent and role are supported by Ghidra and Radare2, but the callback ABI and complete state layout are not established here.

The fresh assembly cross-check resolves the callback target's ABI mismatch. Retail `0x004DFA50` is 3,508 bytes / 68 blocks and takes two cdecl stack arguments according to Radare2. Ghidra decompiles `void FUN_004dfa50(int, undefined4)` and the caller at `0x004DEEC0` pushes the same object pointer twice. The GameNatives candidate `004DFA50-Render_MagicObjectTypeSNotD.cpp` instead declares one argument and an `int*` return, so that interface cannot be copied into the engine as-is. The lifecycle wrapper is one cdecl argument; Ghidra's low-confidence API projection guessed stdcall, but both its `RET` epilogue and Radare2's x86 analysis support cdecl. The factory dispatches through `0x00A96AE0` using `(backend_id & 0xFF) * 0x180 + type_id * 4`; the indirect callback receives object and context pointers, followed by caller cleanup of eight stack bytes. Durable evidence, including the actual R2 block/edge/argument counts and Ghidra evidence IDs, is in [magic-object-lifecycle.json](evidence/magic-object-lifecycle.json). Callback-specific types/behavior and the complete object state layout remain unresolved, so this evidence narrows the transcription work but does not justify wiring guessed callback implementations.

The registration path is also confirmed in the binary: `0x004D9A00` registers `MagicObj` as task type size `0x138` and installs lifecycle handlers; `0x004E0840` registers `MagicObjContainer` as size `0x24`; `0x004E0930` constructs container tasks; and `0x004E0920` closes the container update event. Ghidra and Radare2 agree on the one-block cdecl boundaries for these registration helpers. The diagnostic scene does not invoke this QTask registration/creation lifecycle; it creates host `PlacedModel` children directly. The updated evidence artifact records these additional natives and strengthens the identified gap between parsed/drawn ATTA data and retail MagicObject task behavior.

## Compile/run verification gate (2026-10-18)

The project stores native criteria in `skills/igi-native-verification/SKILL.md` and binary-bound records in `docs/fidelity/native-verification.json`. The current `build.sh`, `igi_retail_engine` CMake target, and `run.sh` check every production `engine/src/retail/*.cpp` regardless of Git status. Each entry must meet `VERIFIED`, including exact binary and source hashes, reviewed signature evidence, Ghidra/Radare2 CFG score of at least 0.85, and a reviewed candidate-vs-retail parity record with durable evidence. Structural agreement between Ghidra and Radare2 is not candidate parity. The pre-commit hook checks staged native files as an earlier filter. The current production tree fails this gate; no build or launch through these paths is permitted until its native evidence records are complete. This policy cannot prevent manual launch of an older executable already on disk.
