# The 0x00000181 pattern in retail `.data` (verified 2026-10-25)

Status: OBSERVED, meaning unproven. Recorded so five sightings are treated as one pattern
rather than five coincidences.

## The observation

Five `.data` slots that the transcribed task registrars write their 16-bit class id into all
carry the same image dword `0x00000181` (385 decimal):

| slot | written by | image dword |
| --- | --- | --- |
| `0x00540B08` | earlier registrar work | `0x00000181` |
| `0x0053C46C` | earlier registrar work | `0x00000181` |
| `0x0053F520` | earlier registrar work | `0x00000181` |
| `0x005410D0` | `0x00488800` `Task_DefineEditVariable` | `0x00000181` |
| `0x00541094` | `0x00487BE0` `Task_DefineGuardGenerator` | `0x00000181` |

Read directly from the image with `r2 -c "pxw 4 @ <VA>"` on
`igi.exe` sha256 `dea34892d417715873ea61d7b2ba5556655f1ad65385104348146f9679915a01`, not taken
from a worker report.

Every one of these slots is written by a **16-bit** store (`66 a3 <dir32>`), and every reader
in the transcribed natives re-loads it with a 16-bit load (`mov ax/cx/dx,[slot]`), which is why
those slots are declared as two `std::uint16_t` words rather than one 32-bit dword.

## New evidence (same day, from `0x00486900`)

`0x00486900` shows `0x181` used a second, different way, verified by me in the image rather
than taken from a report:

```
0x0048691B   push 0x181                 ; 385
0x00486926   call 0x4017C0              ; QTask_AllocateEvent
0x0048692B   mov byte [0x540B5C], al    ; the allocator's LOW BYTE, stored to a slot
```

Here `0x181` is a **pushed immediate passed to an event-id allocator**, and what is stored is
the allocator's returned low byte - not an image dword copied into a slot. That is a different
use from the five data slots above. It does not settle their meaning, but it does establish
that `0x181` is a real id-like constant this binary allocates and caches at run time, and
`0x00467D90` lazily allocates the same value, so there are at least two independent allocation
sites. That fits reading 2 (a pre-assigned id) better than reading 1 (a pure sentinel). This
note still asserts neither.

Note also that `0x00540B5C` is written here as a **byte**, while the five slots in the table
above are written as 16-bit words. Access widths differ per slot and must be read per native; a
blanket "these are all 32-bit id fields" assumption would be wrong in both cases.

## Direct support for reading 2 (verified in the image)

The parent getter `0x004E0830` is:

```
0x004E0830   mov ax, word [0x548698]
0x004E0836   ret
```

and `0x00548698` holds `0x00000181` in the image. `0x004813E0` calls that getter and passes the
result to `TaskType_Register` as the **parent type** of `"ExplodeObject"`, before any
registration in the process has run. A parent argument is a task-type id, so `0x181` is a real,
pre-existing type id present in the image - it cannot be a sentinel meaning "unset".

That does not prove what the other slots hold, but it removes the pure-sentinel reading for at
least this use, and it is consistent with the five slots holding a default or pre-assigned id
that each registrar overwrites. Reading 2 now has direct support; reading 1 is weaker. The
meaning of the individual slots is still not asserted.

## A second parent-type slot holding 0x181 (verified in the image)

```
0x004C48C0   mov ax, word [0x547F42]
0x004C48C6   ret
0x00547F42   0x73710181        ; the low word, which this getter returns, is 0x0181
```

`0x004801B0` calls that getter and passes the result as the parent type of `"FireBall"`, again
before any registration in the process has run. So there are now **two independent parent-type
slots whose low word is `0x181`** (`0x548698` via `0x004E0830`, `0x547F42` via `0x004C48C0`),
and both are passed as a parent id. That is the strongest evidence so far for reading 2.

The shape of the second slot is also informative: its dword is `0x73710181`, i.e. the two bytes
after the id are `0x71 0x73` = `"qs"`. The slot is a 16-bit field sitting inside data that also
carries text, which is exactly why these fields are read with `mov ax, word [...]` and not as
dwords, and why the port declares them as words.

Not every parent getter returns `0x181`: `0x00503BF0` is `mov ax, word [0xA7A62A]` with image
value 0. So `0x181` is a specific type id, not a universal default.

## A third use: the same slot as a class id at link time

`0x0047CF70` takes its class id for two links from getters rather than from a freshly registered
type:

```
push 0x0047D380 ; push eax ; call 0x004C48C0 ; push eax ; call 0x00401400   ; link(class = getter, ...)
push 0x0047E0C0 ; push eax ; call 0x004E5350 ; push eax ; call 0x00401400   ; link(class = getter, ...)
```

with the event id coming from `QTask_AllocateEvent(0)` and cached at `0x00540904`. So
`0x004C48C0`'s slot `0x00547F42` is used as a **class id at link time**, not only as a parent at
registration time. What that slot holds at that moment is whatever the registrar that owns it
has written, so this note does not claim it is `0x181` there - only that the same word is read
for two different purposes (parent id, class id) by two different natives.

## Witnesses 4, 5 and 6, and a candidate `.data` that reproduces them (verified)

`0x00477220` registers three sibling types whose id slots all hold `0x0181` before
`TaskType_Register` overwrites them. Read from the image:

```
0x00540 74C   0x01810181 0x00000181     ; bytes: 81 01 81 01 81 01 00 00
```

Three consecutive 16-bit slots of `0x0181` at `0x54074C`, `0x54074E`, `0x540750`, followed by two
unreferenced bytes. Each is written with a 16-bit store and read back with a 32-bit load masked
by `0xFFFF`, and the candidate's `.data` section is `81 01 81 01 81 01 00 00` - byte-identical to
the image, including the two bytes that are not modelled.

In the same registrar the parent getter `0x004D9FA0` is `mov ax, word [0x548648]`, and
`0x00548648` holds the dword `0xFFFF0181`, whose low word is again `0x0181`. So `0x0181` appears
as a parent value and as a pre-registration id value inside one body.

That is six observed slots now: `0x548698`, `0x547F42`, `0x548648`, `0x54074C`, `0x54074E`,
`0x540750`. The "real type id these slots are seeded with" reading is stronger than before.
`0x00503BF0` returning `0` remains the counter-witness that stops the value being universal, which
is why this note still does not claim a meaning for any individual slot.

## Scope narrowed: `0x0181` is cluster-specific, not a global seed

A counter-witness **family** was found while transcribing `0x00475AC0`: all seven id slots in the
`0x5BE3xx` cluster are image `0`. Verified in the image:

```
0x005BE39C  0x00000000     0x005BE3A8  0x00000000     0x005BE3C0  0x00000000
0x005BE3A0  0x00000000     0x005BE3B8  0x00000000     0x005BE3C4  0x00000000
0x005BE3C6  0x00000000
```

Every `0x0181` sighting so far sits in the `0x5406xx`, `0x5407xx`, `0x5486xx` or `0x547Fxx`
clusters; every slot seen in the `0x5BE3xx` cluster is zero. So the honest statement is not "id
slots are seeded with `0x181`" - it is "in the twelve slots seen so far, six in one cluster family
carry `0x0181` and seven in another carry `0`". The `0x00475AC0` id slot has exactly the same
shape as the `0x0181` ones (16-bit store, dword load masked with `0xFFFF`) and still holds zero,
which is what makes the value a per-cluster fact rather than a property of the access pattern.

A seventh sighting extends the scope again, and it is the HumanPlayer id slot. Verified in the
image:

```
0x005385B0  0x00000181  0x00408770  0x00408a40  0x00408c30
```

`0x0040FE30` registers task type `"HumanPlayer"` (object size `0xDF0`) and stores the returned id
with a 16-bit store at `0x005385B0`, whose image value is `0x0181`. That slot is in the `0x5385xx`
cluster, which is **not** one of the `0x5406xx`/`0x5407xx`/`0x5486xx`/`0x547Fxx` clusters, so the
"one cluster family" phrasing above is too narrow. What survives is the pair of facts: `0x0181`
appears as a pre-registration id in at least five clusters, and the `0x5BE3xx` cluster is entirely
zero. The value is therefore neither universal nor confined to one region, and the honest summary
is "`0x0181` is what many - not all - id slots hold before the registrar overwrites them".

The three dwords following the HumanPlayer id are handler immediates (`0x00408770`, `0x00408A40`,
`0x00408C30`), not related to the pattern.

## Sightings 8 and 9, and a storage-class correlation

`0x00472670` registers two types in one body and both id slots hold `0x0181`:

```
0x005402FC  0x01810181      ; 0x5402FC (GunCAClip) and 0x5402FE (GunCABarrel)
```

`0x005402xx` is a fifth distinct cluster carrying the value. Both slots are written with 16-bit
stores and read back with two different zero-extension encodings (`mov ecx,[abs]; and ecx,0xFFFF`
and `xor edx,edx; mov dx,[abs]`).

The mechanically interesting part: a slot holding `0x0181` cannot live in `.bss`, so these are the
first `0x0181` id slots that are `.data`. Verified on both sides - the image holds `0x0181` at
`0x005402FC`, and the candidate's objects report

```
native_472670.o:  D _g_5402fc    D _g_5402fe      (image 0x0181)
native_4733f0.o:  B _g_5be36c                     (image 0)
```

So the value is not merely a data pattern: it moves the storage class, and the storage class is
independently checkable. That yields a falsifiable prediction for every future `0x0181` slot - it
should appear as `D` in the candidate's symbols, and an image-zero slot as `B`. If a slot reported
as `0x0181` ever comes out `B`, either the image value or the transcription is wrong.

## What is established, and what is not

Established: the five slots share one initial value; the access width is 16-bit on both the
store and the loads; the upper word of each slot is `0x0000` in the image.

Not established: what `0x181` means. Two readings fit the bytes equally well, and the evidence
collected so far does not separate them:

1. a sentinel such as "no class registered yet", overwritten at startup by the registration
   this code performs; or
2. a pre-assigned id that `TaskType_Register` returns and the store merely writes back.

The second reading is the one that would matter for fidelity, because it would mean the value
is data, not code. It can be settled by observing the slot before and after `TaskType_Register`
returns in a runtime capture, which is not available for these natives yet. Until then this
note records the pattern only, and no native asserts a meaning for it.

## Why this is worth a note

Five independent functions writing 16-bit ids into five slots that all start at `0x181` is
either a real property of the retail data layout or a systematic transcription error repeated
five times. Recording the pattern makes the second possibility checkable: if a later native
reads one of these slots before any registrar runs, the sentinel reading is wrong.


## Sightings 13-18 (2026-10-25, `chain-worker`, `0x004682F0` and `0x00467700`)

Six more locations holding `0x0181`, and the first case that **falsifies the address heuristic** that was creeping into the rule:

| Location | Kind | Section from `objdump -s` |
| --- | --- | --- |
| `0x0053F6D0` | id slot of ComputerHilight, 4 bytes before the name literal `0x0053F6D4` | `.data` (`81 01 00 00`) |
| `0x0053F580` | id slot of ComputerObject | `.data` |
| `0x00548698` | loaded by parent getter `0x004E0830` | `.data` |
| `0x0054E634` | loaded by parent getter `0x005034D0` | `.data` |
| `0x0054E200` | loaded by `0x004F45F0` | `.data` |
| `0x00547F42` | loaded by `0x004C48C0` | `.data` |

`0x0053F6D0` is the important one. It sits inside the `0x0053F6xx` region where all the string literals live, so an "addresses in this region are read-only" heuristic would put it in `.rdata` - and it is in `.data`, because its image value is `0x0181`. **The section is not where the address looks; it is what the image value says.** That is the sharper form of the rule and it is now the form to apply.

Cluster count: twelve sightings across nine clusters (`0x5406xx`, `0x5407xx`, `0x5486xx`, `0x547Fxx`, `0x5385xx`, `0x5402xx`, `0x5401xx`, `0x53FExx`, `0x53F6xx`, `0x54E6xx`, `0x54E2xx`). Six agree with the reading "`0x0181` is the pre-registration/base type id" and **no counterexample exists in either lane's range**. The reading is still not written into any source file: what is recorded is that a slot holding `0x0181` cannot be `.bss`, and that the six sites that both hold it and are consumed as a type id agree.

**What would settle it**: a sighting where a slot holding `0x0181` is *written* with some other value before it is used as a type id, or one consumed as a type id that holds something other than `0x0181` and is not an id slot. Neither has appeared.

## The sixth-argument shape, sixth confirmation (`0x004682F0`)

`0x005BDC90` holds image value 0, the body writes `0x13` into it at `0x004682F6`, and its **address** is append 4's sixth argument - so the same body both initialises the object and publishes its address as `arg6`. That is the predicted shape (NULL or the address of a static object, never a type id, never a small integer) seen from the initialising side for the first time.

## Derived-cleanup measurements so far

`0x38`, `0x3C` and `0x2C` across three structurally parallel bodies, with every difference accounted for push by push: `0x3C` minus `0x38` is exactly the `QTask_AllocateEvent` argument, and `0x2C` is a registrar that pushes no allocation argument at all. No cleanup constant may ever be carried across bodies.
