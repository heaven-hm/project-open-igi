# Argument 6 of 0x004F1A80 is a real field, and "inert" is the wrong word for it

Recorded 2026-10-25. This corrects a ruling I issued earlier in the same session.

## What the callee actually reads

`0x004F1A80` (`Script_TaskContainer_Append`, 105 bytes, ends at the `ret` at
0x004F1AE8) loads the same textual offset `[esp+0x20]` **twice**, and the two
loads name **different arguments**, because a `pop` happens between them:

    0x004F1AB1  mov bl, byte [esp+0x20]    esp = esp0-0x0C  -> [esp0+0x14] = ARG5 (byte)
    0x004F1AB5  mov [esi+edi], ecx         record+0x00 = arg3 - arg2
    0x004F1ABD  pop edi                    esp = esp0-0x08
    0x004F1AC1  mov [ecx+esi+4], edx       record+0x04 = ARG4, the parameter type
    0x004F1ACA  mov esi, dword [esp+0x20]  esp = esp0-0x08 -> [esp0+0x18] = ARG6 (dword)
    0x004F1AD1  mov [edx+ecx+8], esi       record+0x08 = ARG6
    0x004F1ADE  mov byte [edx+ecx+0xC], bl record+0x0C = ARG5

All six arguments are read. Argument 4 is the parameter type tested against -1
(0x004F1A8E, fatal `"Undefined parameter type."` at 0x004F1A93 then a spin at
0x004F1AA0). Argument 5 is a **byte** written at `record+0x0C`. Argument 6 is a
**dword** written at `record+0x08`.

**The trap, named:** deriving the frame offset once and reusing it. `[esp+0x20]`
is arg5 before the `pop` and arg6 after it. A reading that resolves the offset a
single time concludes arg6 is never touched, which is what I concluded and what
would have produced 35 call sites writing a wrong dword at `record+0x08`.

## How the call sites are shaped

Retail pushes six words at every site, and the first two are **deferred**: they
sit before an intervening argument-less getter call and are consumed by the
following `0x4F1A80` call.

    0x00406502  push 0        <- ARG6
    0x00406504  push 7        <- ARG5
    0x00406506  call 0x4F0EF0 argument-less: mov eax,[0xA75898]; ret
    0x00406512  push eax      <- ARG4
    0x0040651f  push ecx      <- ARG3
    0x00406520  push edx      <- ARG2
    0x00406521  push eax      <- ARG1
    0x00406522  call 0x4F1A80
    (the closing add esp,0x18 is shared and comes later)

Six pushes, six dwords, matching the tree's six-parameter declaration. The
same shape appears at 0x004888E6/0x004888E8, and the tree's own comments there
already label the two pushes "(arg6)" and "arg5" - the existing transcription had
the arity right.

## Argument 6 is not always 0

Measured in `0x004310F0` (`Task_DefineHeli`): eleven appends push 0, but append 3
pushes the return of `0x004F1C90` (the pointer to the pair it just initialised at
0x00A76BF0) and append 13 pushes the immediate address `0x0057BD38`. Both are
reproduced as real values, because both are written to `record+0x08`.

In `0x00406450` the per-site values are 0 at 0x00406522, `0x5690C0` four times,
`0x5690B8` once, and a producer's return at the remaining sites.

## Audit of the existing corpus

128 `Script_TaskContainer_Append` call sites in `engine/src`. **104 pass `0` as
the sixth argument**, and a few pass real pointers (`0x005C1170` x5,
`0x005C1178` x2, `&g_a7b2b8` x1). Spot-checked against the image, the `0` sites
that carry a provenance comment show retail genuinely doing `push 0` there - for
example `core/native_488800.cpp:150` annotates `0x00488908/0x0048890A: push 0;
push 7`, and `0x00488908` is `6a 00` in the image.

So the **values** in the corpus look faithful; what is wrong is the **label**.
Several provenance comments call those pushes "inert", which is false - they are
arguments 5 and 6, and argument 6 is stored. The label is what led me to the
wrong ruling, so it is the thing to fix: a future transcriber reading "inert"
will flatten a real value.

## Outstanding, deliberately not fixed speculatively

Any tree site that passes `0` without its provenance showing retail `push 0` at
that site would write the wrong dword at `record+0x08`. That is a targeted
verification task over the ~20 files with `0x004F1A80` call sites, to be run
after the `0x00402930` guard list closes. It is not evidence of a defect in any
particular file; it is an unverified claim that should be checked rather than
assumed either way.
