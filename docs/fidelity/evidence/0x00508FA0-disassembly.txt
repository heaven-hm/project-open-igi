`0x4F1980` decode begins: it takes (container, count), computes `*container + count`, calls
`0x004F1950` with that, then copies `*container * 16` bytes from `container+8` to

Its own callee `0x4F1950` is the next leaf to check.

### 0x4F1950 decoded (41 B, 1 block) - allocation helper for 0x4F1980

```
esi = arg            ; element count
eax = count << 4; eax += 12
call 0x4B0C60(eax, 4)        ; cdecl: push 4, push (count*16+12) -> allocator
eax[4] = count
eax[0] = 0
eax[8] = eax + 12            ; payload pointer stored in header
ret
```

So the container is a 12-byte header {0, count, payload} plus `count*16` bytes of
payload allocated through `0x4B0C60` with flags 4. That explains `0x4F1980`: it grows
the container by `count`, reallocates through this helper and copies the old payload with
`rep movsd`/`rep movsb` in retail's 4/1 split.

Next dependency: `0x004B0C60` (allocator). If it is not in the tree, both `0x4F1950` and
`0x4F1980` stay blocked and the allocator is the leaf to land first.

### 0x4F1A80 decoded (105 B, 4 blocks) - appends a 16-byte record to a container

```
ecx = arg3; edx = arg2; ecx = arg3 - arg2
edx = arg4; if (edx == -1) { Debug_Error("Undefined parameter type."); jmp self }
eax = arg1 (container)
push ebx/esi/edi

bl  = byte [arg5 stack slot]                  ; low byte kept for the last field

dword [payload+4]   = edx                     ; record[1] = arg4
dword [payload+8]   = dword [arg5 slot]       ; record[2] = arg5
byte  [payload+0xC] = bl                      ; record[3] = arg5 low byte

```

So it appends one 16-byte record `{arg3-arg2, arg4, arg5, arg5&0xFF}` at
`payload + count*16` and increments the container count - consistent with the 16-byte
stride established by `0x4F1950`/`0x4F1980`. Features preserved: the `arg4 == -1`
fail-closed path calling `Debug_Error("Undefined parameter type.")` then spinning
forever, and the same record written through four separate `count*16` recomputations
(retail reloads the count each time; a transcription that caches it would still be
observably equivalent only because nothing modifies the count in between - the retail
reload pattern is recorded here so it is not silently "optimised").

### 0x4F1A80 argument layout: contradiction found, unresolved (round 55)

Counted the pushes at **all seven** `call fcn.004f1a80` sites in `0x508FA0`: every one
pushes exactly **four** dwords. Pattern at each site:

```
push eax                    ; value  -> arg4
mov  eax, dword [0xa7b2cc]  ; container global
lea  edx, [var_ch]          ; -> arg2
push ecx                    ; -> arg3 (lea of a local)
push edx
push eax                    ; -> arg1 = container
call 0x4F1A80
```

Callee reads at entry-relative `+4, +8, +0xC, +0x10` map to arg1..arg4 consistently:
arg1 container, arg2/arg3 pointers to locals, arg4 a value. But the body also reads a
**fifth slot** 4 bytes above arg4 (`bl = byte [...]`, then a dword from the same slot)
while the callers push only four dwords. Under plain cdecl that extra read lands on the
caller's own stack word, not on an argument.

Two explanations remain, and neither is yet proven:

1. retail genuinely over-reads one caller stack word here (the AI-graph parameter record
   gets a field from unrelated caller state - a retail quirk that must be reproduced,
   not fixed), or
2. one push is not visible in the linear listing as a `push` mnemonic (e.g. a store-based
   argument passing) and there really are five arguments.

Until disambiguated, `0x4F1A80` stays TRANSCRIBED-NOT-WRITTEN. Choosing either guess would
put a fabricated ABI under the AI-graph registrar. Next evidence: read the caller's own
frame around `0x00509153` (what `[esp+0x14]` holds at the call) or compare with a
decompiler view of the same site; the caller body is single-block, so its locals are fully
visible.

### 0x4F1A80 ABI RESOLVED: fifth argument is passed via the previous call's stack leftovers

Reading the caller at `0x00509136-0x00509158` settles the contradiction:

```
push 0
push 7
call 0x4F0F80              ; 2 args, NOT cleaned here
lea ecx,[var_88h]; push eax
mov eax,[0xa7b2cc]; lea edx,[var_ch]
push ecx; push edx; push eax
call 0x4F1A80             ; 4 explicit pushes
add esp, 0x18             ; 24 bytes = 6 dwords cleaned at once
```

The single `add esp,0x18` cleans **both** the two `0x4F0F80` arguments and the four
`0x4F1A80` arguments - the two-argument push pair is still on the stack when `0x4F1A80`
is called. So at `0x4F1A80`'s entry:

- `+4` container, `+8` local pointer, `+0xC` local pointer, `+0x10` value (its four
  declared pushes),
- `+0x14` = **7** (the leftover first argument of the preceding `0x4F0F80` call),
- `+0x18` = 0 (its second leftover).

The body's "fifth slot" read (`byte` at `+0x14`, then a dword from the same slot) therefore
reads the *deterministically present* leftover argument - not uninitialised caller memory.
Second site confirms the mechanism with 5 instead of 7. So the routine takes **five**
arguments, with the fifth supplied by stack reuse rather than an explicit push before its
own call.

Consequence for transcription: declare five parameters and pass the fifth explicitly with
the same value the preceding `0x4F0F80` call receives (7, then 5, ...). That preserves the
record field and the stack-argument semantics without pretending a fifth push exists in the
listing. The four `record` writes and the count reload pattern stay exactly as decoded.
Blocker therefore cleared: `0x4F1A80` is writable once `0x4F0F80` (already transcribed,
called 6 times) is confirmed to be its source of the fifth value at every site - which the
`add esp,0x18` cleanup count at each of the seven sites can verify mechanically.

### 0x4C04B0 semantics settled from the prologue bytes


### 0x4C0360 complete decode (87 B, 5 blocks) - bucket array with self-linked sentinels

```
h = Mem_Alloc(8)                ; 0x4C0362/0x4C0366 (8 in arg1 slot; the pushed 4 is stray)
h[4] = count                    ; 0x4C0376
size = count*12 (lea + shl 2)   ; 0x4C0373/0x4C0379
h[0] = Mem_Alloc(size)          ; 0x4C037C/0x4C037D - note: ONE pushed argument here
if (count <= 0) goto end
for (i = 0; i < count; ++i) {
    bucket = h[0] + i*12
    bucket[0] = bucket + 4      ; 0x4C0397: next -> own +4
    bucket[8] = bucket          ; 0x4C03A1: back-pointer -> self
    bucket[4] = 0               ; 0x4C03A6: cleared
}
return h                        ; 0x4C03AD: mov eax,esi
```

**Arity observation worth recording:** the two `Mem_Alloc` calls in this function push a
different number of arguments - `push 4; push 8; call` for the header but `push eax; call` for
the bucket block. CORRECTION (round 93): `Mem_Alloc` DOES read two arguments - `mov eax,[esp+4]`
and `mov ebx,[esp+0xc]` feeding `lea ebp,[eax+ebx+0x1c]` - so the second call is not exempt: its
arg2 is the leftover pushed `8` still on the stack (stack reuse, the same pattern as 0x4F1A80),
i.e. `Mem_Alloc(count*12, 8)`, and `add esp,0x10` cleans all four dwords, the
same benign pattern already documented for `0x4D9730`. The engine's current
`Mem_Alloc(std::int32_t context, std::int32_t arg2)` therefore needs checking against retail
before it is called from a faithful transcription, because reading a second argument would make
the stray-push call wrong.

With this, `0x4C0360` is otherwise self-contained: no globals, one callee, and the 12-byte
self-linked bucket layout matches what `0x4C04B0` walks (`next` at +0, key at +8, back at +4/-4
as the inserts use).
